batch-http-appender — performance

Stock Log4j2 HttpAppender vs. the batching HTTP appender (v0.1.3), measured on four Mule apps — a batch/stock pair shipping to Datadog and a second pair shipping to New Relic — on both CloudHub 1.0 and CloudHub 2.0.

Targets: CloudHub 1.0 & 2.0 Worker: 0.1 vCore Vendors: Datadog & New Relic Load: oha, 5 connections, 60 s, plain http Endpoint: /log?count=15 — 17 events/request Warmup: 5 requests, 10 s pause Pairing: paired-parallel, one vendor per side Measured: 2026-08-03 appender: v0.1.3
Against its own stock sibling, on the same platform, shipping to the same vendor, the batching appender sustained the full 60 s at 16–18× the request throughput on CloudHub 1.0 for both vendors and 1.2–3.8× on CloudHub 2.0 — every one of the eight runs at 100% success. The vendor barely matters; the platform does. That pattern is consistent with a CPU-capped CloudHub 2.0 replica being bottlenecked upstream of the appender, while a CloudHub 1.0 worker leaves headroom a synchronous appender cannot use — offered as the explanation the data fits, not as something these runs measured. The two platforms have different CPU models, so each figure holds within its own plane and the two are not a comparison of each other; see the caveats below. The stock appender's synchronous one-POST-per-event send holds the request thread for the whole round-trip to the intake, so under concurrency its small thread pool saturates and its tail climbs into the multi-second range — p99 between 9.5 s and 22 s on three of the four stock runs, the CloudHub 2.0 Datadog run being the exception at 1,105 ms. The batch appender's non-blocking enqueue keeps request latency decoupled from intake latency.

The appender code is the same across all four apps, and within each vendor-and-platform pair the batch-vs-stock contrast is what holds. Across the four pairs the spread is 16–18× on CloudHub 1.0 against 1.2–3.8× on CloudHub 2.0 — the platform moves the result far more than the vendor does. The explanation that fits is a CPU-capped CloudHub 2.0 replica bottlenecked upstream of the appender, against a CloudHub 1.0 worker with headroom a synchronous appender cannot use; these runs did not measure that mechanism directly. Read each table against its own stock column, not against a table on the other platform — the two generations have different CPU models. See the caveats below.

What was tested

Two batch/stock pairs of functionally identical Mule 4 applications — one member of each pair on Log4j2's stock <Http> appender, the other on this library's <BatchHttp> (v0.1.3) — one pair shipping to the Datadog Logs intake and one to the New Relic Logs intake, all four deployed to each platform. Within a pair the apps share the same flow, the same <Loggers> wiring, and the same file appender; the only substantive difference is the appender element. Each request to /log?count=15 emits 17 log events — a batch.start, 15 order.processed, and a batch.completed. The same count=15 was used on both platforms:

  • Stock — Log4j2's built-in HttpAppender: one synchronous HTTP POST per log event.
  • Batch (0.1.3) — this library's <BatchHttp> appender: events are enqueued non-blocking and shipped in batches by background threads.

Load was generated with oha (--no-tui -z 1m -c 5) at 5 concurrent connections for 60 seconds over plain http. Each app was first primed with a 5-request warmup (to prime the JVM's JIT, the connection pool, and the batch flusher) followed by a 10 s pause before the measured run — this eliminated the first-run throughput swings a lighter single-request warmup produced. The "aborted due to deadline" entries are in-flight requests cut off at the 60 s mark.

The two vendors were driven paired-parallel, one vendor per side: each phase put a Datadog app and a New Relic app under load at the same instant — the two batch apps together, then the two stock apps together — so no vendor's intake was ever loaded by two apps at once and neither app of a comparison waited on the other's intake. Measured 2026-08-03. Every one of the eight runs completed the full 60 s at 100% success.

Each run independently corroborates the load parameters: requests/sec × mean latency ≈ the concurrency of 5 (Little's Law) holds to within 0.1–16% across all eight. Three runs — the CloudHub 1.0 stock pair and the CloudHub 2.0 New Relic stock run — needed a ×10 latency correction for a known oha 1.14.0 unit-selection defect, which prints a 0.0774 10 sec-shaped value where it means 0.774 sec. Every figure on this page is already corrected; the correction touches latency only, not request counts or requests/sec.

Sample log event

The flow emits each event as a JSON object — byte-for-byte identical across the two apps of a vendor pair so the payload never skews the comparison. (The New Relic pair leads its object with an extra message summary key, which that vendor's Logs UI requires; the Datadog pair does not. That difference is between the two pairs, never inside one, so each batch-vs-stock contrast is still payload-identical.) The flow writes it pretty-printed (multi-line, so the CloudHub file log stays human-readable) and the vendor appender's layout collapses it to one line, ~240–350 characters. A representative order.processed event from the Datadog pair, as the intake receives it:

{"generatedAt":"2026-01-01T00:00:00.000Z","event":"order.processed","orderId":"b3b1f2c4-5d6e-47a8-9f01-23456789abcd","sequence":1,"of":15,"level":"info","region":"region-a","source":"mule","customer":"cust-1","amount":19.95,"currency":"USD","orderStatus":"SHIPPED","warehouse":"wh-a-03","carrier":"expedited-air","note":"synthetic order event emitted to exercise the log pipeline end to end"}

Built in the Mule flow as a DataWeave string literal (the multi-line, indented form the FILE appender keeps verbatim); the vendor appender's %replace{%m}{^\x7B\s*|[\r\n]+\s*}{} strips the leading brace and every newline+indent to yield the single line above. generatedAt (UTC ISO-8601) is the flow's own first field — when the business event occurred, emitted by the DataWeave expression rather than by the appender, so both halves of the pair report the same clock reading. The vendor's service, host and platform facets are added from config — see "Logging configuration under test" below. Note the message itself carries no service/host: those identity facets come from log4j2.xml, not the log line. A run at count=15 wraps the loop with a batch.start (INFO) and a batch.completed (WARN); /boom emits an order.failed (ERROR) with a stack trace.

Why the stock appender stalls: its per-event send holds the request thread for the full round-trip to the intake API. Under 5 concurrent clients — each firing 17 events per request — the worker's small thread pool saturates, so most requests queue behind an in-flight HTTP send. That is the bimodal latency three of the four stock runs show: a median in the low hundreds of milliseconds against a p99 of many seconds. The batch appender returns from the logging call immediately, so request latency is decoupled from intake latency. The CloudHub 2.0 Datadog stock run is the one that does not do this — see that section for what it suggests instead.
Caveats — read the numbers as directional, not absolute. All seven apply to every figure on this page.
  • One run per pair, no median. Each of the four vendor-and-platform pairs was measured once. Nothing here is a median of repeated passes, so the pattern is directional, not established.
  • Roughly 2× run-to-run variance has been observed on CloudHub 1.0 across repeated passes. The CloudHub 2.0 Datadog figure of 1.19× sits inside that band and is therefore directional only — not distinguishable from noise on a single run. The variance is stated as observed; its cause is not established here.
  • The CloudHub 1.0 workers were freshly deployed with no accumulated burst balance, so those runs were measured at baseline CPU rather than on burst headroom. That makes 16–18× a floor rather than a flattering peak — worth stating because it is the opposite of the usual suspicion about a burstable worker.
  • gzip and spillEnabled were disabled in these demos, so this measures batching in isolation rather than the appender as it would be deployed. Compression is off precisely because the stock <Http> appender cannot compress and leaving it on would vary two things at once. See "Logging configuration under test" below.
  • Compare within a plane, not across. CloudHub 1.0 and CloudHub 2.0 have different CPU models — burstable versus hard-capped — so the two platform sections are not a controlled comparison of each other, whatever else was held constant between them. Each table stands as a batch-vs-stock contrast within its own vendor and platform.
  • Throughput and mean latency are one measurement, not two. The load is closed-loop: oha at 5 connections with no rate limit keeps five requests in flight at all times, so requests/sec is the arithmetic consequence of mean latency (concurrency ÷ mean latency). The req/s row and the average-latency row are the same result viewed twice, not two independent wins. The percentiles are unaffected.
  • One observed and unexplained artifact. On both CloudHub 1.0 batch apps, exactly five requests — matching the concurrency — stalled together for several seconds and then recovered: near 4.4 s on the Datadog app, near 6.1 s on the New Relic one, against medians of 35 ms. It is five requests in roughly five thousand and moves neither the medians nor the ratios. Reported as observed; the cause is unexplained.

Logging configuration under test

The appender config from each app's log4j2.xml (comments stripped). The Datadog pair is shown; the New Relic pair is the same shape with that vendor's own attributes and intake, and the batch tuning below is byte-for-byte the same in both batch apps. Both apps of the pair shown ship to the same Datadog Logs intake and set the Datadog service and host facets, plus a platform facet naming the CloudHub generation, from config, not from the log message — via a <Properties> block that is identical in both apps except for the service default, which is each app's own name so the two runs stay separable in Datadog:

<Properties>
    <!-- Datadog facets, from config so per-app identity does not come from the
         log message. Log4j2 lookups, NOT Mule ${...} placeholders. app.service
         identifies the APP and defaults to this app's own name
         (datadog-stock-http in the stock sibling); app.platform identifies the
         PLANE and defaults to "unspecified". Both are settable per deployment
         (-Dapp.service=… / -Dapp.platform=…), and an override you no longer want
         must be DELETED rather than cleared: a property that is present but EMPTY
         beats a ${sys:x:-default} default and silently blanks the facet. host and
         site are the same expression in both. -->
    <Property name="app.service">${sys:app.service:-datadog-batch-http}</Property>
    <Property name="app.platform">${sys:app.platform:-${env:APP_PLATFORM:-unspecified}}</Property>
    <Property name="dd.host">${sys:domain:-${env:HOSTNAME:-${hostName}}}</Property>
    <Property name="dd.site">${sys:dd.site:-${env:DD_SITE:-…}}</Property>
</Properties>

Stock — Log4j2 <Http> (one POST per event)

<Configuration status="WARN">

<Http name="datadog"
      url="${sys:dd.logUrl:-https://${dd.site}
           /api/v2/logs}"
      connectTimeoutMillis="10000"
      readTimeoutMillis="10000">
    <Property name="DD-API-KEY"
              value="${sys:DD_API_KEY:-…:-MISSING_KEY}}"/>
    <Property name="Content-Type" value="application/json"/>
    <PatternLayout pattern='{
      "service":"${app.service}",
      "host":"${dd.host}",
      "platform":"${app.platform}",
      %replace{%m}{^\x7B\s*|[\r\n]+\s*}{}'/>
</Http>

Batch — <BatchHttp> 0.1.3 (batched)

<Configuration status="INFO"
    packages="com.mulesoft.support.batchhttp.log4j2">

<BatchHttp name="datadog"
           vendor="datadog"
           site="${dd.site}"
           apiKey="${sys:DD_API_KEY:-…:-MISSING_KEY}}"
           service="${app.service}"
           host="${dd.host}"
           source="mule"
           maxBatchRecords="200"  maxBatchBytes="900000"
           lingerMillis="2000"    queueCapacity="25000"
           gzip="false"           maxRetries="3"
           flusherThreads="1"     includeTimestamp="false"
           spillEnabled="false"   spillFormat="BINARY"
           …spill/diagnostics knobs…>
    <PatternLayout pattern='{
      "platform":"${app.platform}",
      %replace{%m}{^\x7B\s*|[\r\n]+\s*}{}'/>
</BatchHttp>

Both layouts collapse the flow's pretty JSON to one line, and neither stamps a timestamp of its own — generatedAt comes from the flow, so the event time is the same in both apps regardless of appender, and includeTimestamp="false" stops the batch sink adding a competing one. The difference is where the Datadog facets come from: the stock <Http> exposes no service/host attributes, so both are injected into its PatternLayout (its output is the POST body); the batch <BatchHttp> sets them as appender attributes and the sink emits them as top-level envelope facets. Either way Datadog receives the identical top-level service/host. The platform facet comes from the layout on both sides, because the layout is the one mechanism the two appenders share. Stock uses status="WARN" and no packages scan (the <Http> appender ships with log4j-core); batch uses status="INFO" so its diagnostics/heartbeat surface, and packages so Log4j2 discovers the <BatchHttp> plugin.

The batch app also overrides three library defaults, each to keep the comparison to the appender alone. gzip="false" (the library default is true) because the stock <Http> appender has no compression option at all, so leaving it on would vary batching and compression; both apps therefore POST plaintext JSON. spillEnabled="false" (the library default is also true) because the disk-spill buffer adds a replay thread and failure-path disk I/O that the stock appender has no equivalent of — real competitors for a tenth of a core. Every other spill* attribute stays in the file but is inert. includeTimestamp="false" (default true) omits the vendor's reserved event-time field so the vendor stamps its own arrival time and arrival − generatedAt stays readable as ingest lag; the stock siblings' layouts carry no such key either, so both halves are measured identically. A production app would leave compression and spill on, which is why these figures measure batching in isolation rather than the appender as deployed — treat those as separate measurements rather than properties of these demos. The remaining tuning — maxBatchRecords="200", maxBatchBytes="900000", lingerMillis="2000", queueCapacity="25000" and a single flusher thread — is identical across both batch apps.

Async logging — identical in both apps

The <Loggers> block is the same in both apps, so the appender is the only variable. CloudHub requires async appenders, so every logger here is async. Only the application logger routes to the Datadog appender; the root carries the local file alone, because the vendor layout wraps the flow's JSON message and a plain-text framework line would render as an invalid document.

<Loggers>
    <AsyncLogger name="com.mulesoft.support.batchhttp.muledemo" level="INFO" additivity="false">
        <AppenderRef ref="datadog"/>
        <AppenderRef ref="FILE"/>
    </AsyncLogger>

    <AsyncLogger name="com.gigaspaces" level="ERROR"/>
    <AsyncLogger name="com.j_spaces" level="ERROR"/>
    <AsyncLogger name="com.sun.jini" level="ERROR"/>
    <AsyncLogger name="net.jini" level="ERROR"/>
    <AsyncLogger name="org.apache" level="WARN"/>
    <AsyncLogger name="org.apache.cxf" level="WARN"/>
    <AsyncLogger name="org.springframework.beans.factory" level="WARN"/>
    <AsyncLogger name="org.mule" level="INFO"/>
    <AsyncLogger name="com.mulesoft" level="INFO"/>
    <AsyncLogger name="org.jetel" level="WARN"/>
    <AsyncLogger name="Tracking" level="WARN"/>

    <AsyncRoot level="INFO">
        <AppenderRef ref="FILE"/>
    </AsyncRoot>
</Loggers>
