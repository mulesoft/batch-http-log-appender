batch-http-appender — performance

Stock Log4j2 HttpAppender vs. the batching HTTP appender (v0.2.0), measured on sixteen Mule apps — a batch/stock pair shipping to each of Datadog, New Relic, Elasticsearch and Dynatrace, on both CloudHub 1.0 and CloudHub 2.0 — with the logs delivered counted at every vendor. Datadog, New Relic and Elasticsearch were measured on 2026-10-12 as three parallel lanes; Dynatrace was measured on 2026-10-13, its lane alone, with the same protocol, sizes, region and build. Headline figures are the 5-minute sustained run (Test 3); see the cold-start caveat below for why the 1-minute run reads lower.

Against its own stock sibling, on the same platform, shipping to the same vendor, the batching appender sustained a 5-minute run at 6.5–139.5× the request throughput on CloudHub 1.0 and 4.4–59.5× on CloudHub 2.0, and delivered every log to Datadog, Elasticsearch and Dynatrace in every test. The low end of each range is Dynatrace: its batch app ran at the same req/s as the other vendors' (135 on CloudHub 1.0, 41 on CloudHub 2.0), so the worker, not the vendor, bounds batch; but a single-record POST to its in-region intake is quick, so the stock appender is penalised far less there. The stock appender's synchronous one-POST-per-event send holds the request thread for the whole round-trip to the intake, so under concurrency its single background flusher never catches up and its tail climbs into the multi-second — sometimes tens-of-seconds — range. The batch appender's non-blocking enqueue keeps request latency decoupled from intake latency. The two planes run at different concurrency (CH1 -c 10, CH2 -c 5) because their CPU models differ, so each figure holds within its own plane and the two are not a comparison of each other — see the caveats below.

What was tested

Four batch/stock pairs of functionally identical Mule 4 applications — one member of each pair on Log4j2's stock <Http> appender, the other on this library's <BatchHttp> (v0.2.0) — one pair shipping to the Datadog Logs intake (site ap2, Sydney), one to the New Relic Logs intake (US, log-api.newrelic.com), one to Elasticsearch (Elastic Cloud Serverless, Sydney) and one to Dynatrace (Dynatrace SaaS on AWS, Sydney), all eight deployed to each platform (sixteen apps total). The sample Mule projects are in the repository and linked from each vendor page. Within a pair the apps share the same flow, the same <Loggers> wiring, and the same file appender; the only substantive difference is the appender element. The batch apps run maxBatchRecords=200, one flusher, gzip="false" and disk spill on. Each request to /log?count=20 emits 22 log events — a batch.start, 20 order.processed, and a batch.completed.

Load was generated with oha 1.16 (-w) over a 5-minute window (Test 3). Concurrency differs by plane — CloudHub 1.0 at -c 10 over http, CloudHub 2.0 at -c 5 over https — because the CloudHub 2.0 replica is a capped-CPU, no-swap worker held at lower concurrency to stay off its OOM ceiling. Because -c differs, compare only within a plane (batch vs stock), never CloudHub 1.0 against CloudHub 2.0. Every worker and replica runs in Sydney (ap-southeast-2).

Datadog, New Relic and Elasticsearch ran on 2026-10-12 as parallel lanes, since each has its own intake, with one app per vendor at a time: CH1 batch, CH1 stock, CH2 batch, CH2 stock, with a barrier after each step. Dynatrace ran on 2026-10-13 as a single lane on its own, with the same protocol, the same app and worker sizes, the same region and the same build. As a control, against a sequential, Elasticsearch-only run of 2026-10-11, Elasticsearch stock req/s in the parallel lanes was within 3% on CloudHub 2.0 in the 5-minute rounds. On CloudHub 1.0 it was −3.3% in Test 4 and −14.6% in Test 3; an earlier parallel round of the same stock apps read +2.9% and −7.1% there, so a single CloudHub 1.0 stock run moves that much on its own. Every test starts on a freshly restarted app (restarts are pipelined ahead of each app's turn), followed by 5 light warmups and a 30 s drain. The exception is the churn window, which follows Test 1 with no restart.

Logs delivered is the logs that reached the vendor divided by the logs the measured requests generated (HTTP 200 responses × 22). Elasticsearch is counted by event time inside the oha window, and so is Dynatrace (in Grail, with DQL, by log.source). Datadog and New Relic are counted by arrival time, from the test's start to the next test on the same app: the demos omit the vendors' reserved event-time attribute on purpose, so the vendor stamps arrival. A value over 100% is late backlog from an earlier test arriving in the window, or log lines of requests oha cut off.

Each 5-minute run shown here independently corroborates the load parameters: requests/sec × mean latency ≈ the plane's concurrency (Little's Law) holds within 8% across all sixteen. It does not hold for every run in the full report: where requests fail or time out (Test 4, New Relic on CloudHub 1.0 in the churn window) or a long stock tail drains past the deadline (the 1-minute tests), the product falls below -c. The parsers still normalise the oha 1.14.0 ×10 unit-selection display glitch, which this run's 1.16 output does not show.

⚠ Cold-start caveat — the 1-minute Test 1 reads lower than this page's headline. The batch appender is CPU/JIT-bound and warmup-sensitive; the warmup before each run is deliberately light so it does not pre-load the stock flusher's backlog. The trade-off is that the batch JVM is still under-warmed when a 1-minute window opens, so a short Test 1 under-reports batch throughput (e.g. CloudHub 2.0 Datadog batch rises 14.4 → 42.0 req/s from the 1-minute run to this 5-minute one as the fixed cold-start cost amortises). The 5-minute Test 3 shown here is the better read of sustained warm throughput. The full Markdown report (docs/benchmark-results.md) carries Test 1, the in-thread churn window, Test 3, and the 30s-cap Test 4 side by side, with logs delivered for each.
Caveats — read the numbers as directional, not absolute.
  • One run per app, no median. These are single measurements, not repeated ones. The pattern is directional, not established.
  • Concurrency differs by plane (CH1 -c 10, CH2 -c 5), so the two platform sections are not a controlled comparison of each other. Each table stands as a batch-vs-stock contrast within its own vendor and platform.
  • Spill is on and gzip is off. Spill costs batch req/s where the queue overflows the whole time (New Relic on CloudHub 1.0 in the churn window: 42 req/s) but not in the 5-minute tests. Compression is off because the stock <Http> appender cannot compress, and leaving it on would vary two things at once; a production deployment should leave it on.
  • Throughput and mean latency are one measurement, not two. The load is closed-loop (oha with no rate limit), so requests/sec is the arithmetic consequence of mean latency, not an independent win. The percentiles are unaffected.
  • New Relic results depend on location. The workers run in Sydney (ap-southeast-2), next to Datadog's ap2 site and the Elasticsearch project. New Relic offers only US and EU regions; these apps ship to the US endpoint (log-api.newrelic.com), so every batch crosses the Pacific (on CloudHub 1.0 in Test 3 the backlog drained at about 330 logs/s). Requests/sec measures how responsive the app stays, not how many logs arrive. New Relic batch delivered about 96–107% in Test 1 and churn, 44.5% (CloudHub 1.0) and 77.3% (CloudHub 2.0) in Test 3, and 100% in Test 4. The Test 3 shortfall is a restart, not a drop: the 5-minute burst spilled to disk faster than the US intake took it, and the backlog was still draining when the next round's restart replaced the worker (CloudHub 1.0 restarts onto a new worker, 2.0 onto a new pod), so /tmp and the spill files went with it. Test 4 was the last round; nothing restarted after it, and its backlog drained in about 12 minutes. Workers closer to the New Relic region, or gzip plus more flusherThreads, ship faster.
  • Stock loses its backlog at every restart. At Datadog, New Relic and Elasticsearch, stock delivered 14–83% of its logs in Test 1 and Test 3: what is still queued in memory when the next restart comes is gone.
  • Dynatrace was measured a day later, on its own. Same protocol, sizes, region and build as the other three, but run 2026-10-13 as the only lane. Its batch÷stock is only 4.4–6.5× in Test 3 (the other vendors: 28–140×) because a single-record POST to the in-region Dynatrace intake takes about 4.4 ms, so the stock appender is penalised far less; batch req/s is the same as elsewhere. Batch delivered 100% in every test on both planes. CloudHub 1.0 stock delivered only 50.7–58.5%: its single serialized background sender reached the intake at a flat rate of about 225 records/s throughout, below what the app generated. CloudHub 2.0 stock's own load sat just under that rate and it delivered 100%. This is not Dynatrace throttling: a 914 req/s single-record burst from a laptop got HTTP 204 for every request and every record was stored. Where the undelivered CloudHub 1.0 stock records were lost is not established; the timing points at the async queue rather than a restart (nothing restarted after Test 4, and a queued backlog would have drained before it was counted).
  • Correction to the 2026-08-04 run. Its CloudHub 2.0 Datadog stock app carried a leftover AsyncLoggerConfig.RingBufferSize=20000 and log4j2.debug=true that no other app had. It measured 5.75 req/s with them against 1.46 without, so the published 7.6× is not comparable; a re-test without them gave about 31×. This run's app has neither property.
