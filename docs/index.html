batch-http-appender — performance

Stock Log4j2 HttpAppender vs. the batching HTTP appender (v0.1.3), measured on eight Mule apps — a batch/stock pair shipping to Datadog and a second pair shipping to New Relic, on both CloudHub 1.0 and CloudHub 2.0. Headline figures are the 5-minute sustained run (Test 3); see the cold-start caveat below for why the 1-minute run reads lower.

Targets: CloudHub 1.0 & 2.0 Worker: 0.1 vCore Vendors: Datadog & New Relic Load: oha, 5 min, CH1 -c 10 / CH2 -c 5 Endpoint: /log?count=20 — 22 events/request Measured: 2026-08-04 appender: v0.1.3
Against its own stock sibling, on the same platform, shipping to the same vendor, the batching appender sustained a 5-minute run at 56–134× the request throughput on CloudHub 1.0 and 8–56× on CloudHub 2.0. The stock appender's synchronous one-POST-per-event send holds the request thread for the whole round-trip to the intake, so under concurrency its single background flusher never catches up and its tail climbs into the multi-second — sometimes tens-of-seconds — range. The batch appender's non-blocking enqueue keeps request latency decoupled from intake latency. The two planes run at different concurrency (CH1 -c 10, CH2 -c 5) because their CPU models differ, so each figure holds within its own plane and the two are not a comparison of each other — see the caveats below.

What was tested

Two batch/stock pairs of functionally identical Mule 4 applications — one member of each pair on Log4j2's stock <Http> appender, the other on this library's <BatchHttp> (v0.1.3) — one pair shipping to the Datadog Logs intake and one to the New Relic Logs intake, all four deployed to each platform (eight apps total). Within a pair the apps share the same flow, the same <Loggers> wiring, and the same file appender; the only substantive difference is the appender element. Each request to /log?count=20 emits 22 log events — a batch.start, 20 order.processed, and a batch.completed.

Load was generated with oha over a 5-minute window (Test 3). Concurrency differs by plane — CloudHub 1.0 at -c 10, CloudHub 2.0 at -c 5 — because the CloudHub 2.0 replica is a capped-CPU, no-swap worker held at lower concurrency to stay off its OOM ceiling. Because -c differs, compare only within a plane (batch vs stock), never CloudHub 1.0 against CloudHub 2.0. Each app was restarted and warmed before every run. Measured 2026-08-04.

Each run independently corroborates the load parameters: requests/sec × mean latency ≈ the plane's concurrency (Little's Law) holds across all eight. Latency figures from oha 1.14.0 may carry a ×10 unit-selection display glitch; every figure here is normalised. The correction touches latency only, not request counts or requests/sec.

⚠ Cold-start caveat — the 1-minute Test 1 reads lower than this page's headline. The batch appender is CPU/JIT-bound and warmup-sensitive; the warmup before each run is deliberately light so it does not pre-load the stock flusher's backlog. The trade-off is that the batch JVM is still under-warmed when a 1-minute window opens, so a short Test 1 under-reports batch throughput (e.g. CloudHub 2.0 Datadog batch rises 13.8 → 43.5 req/s from the 1-minute run to this 5-minute one as the fixed cold-start cost amortises). The 5-minute Test 3 shown here is the better read of sustained warm throughput. The full Markdown report (docs/benchmark-results.md) carries Test 1, the in-thread churn window, Test 3, and the 30s-cap Test 4 side by side.
Caveats — read the numbers as directional, not absolute.
  • One run per pair, no median. These are single measurements, not repeated ones. The pattern is directional, not established.
  • Concurrency differs by plane (CH1 -c 10, CH2 -c 5), so the two platform sections are not a controlled comparison of each other. Each table stands as a batch-vs-stock contrast within its own vendor and platform. (The next benchmark round plans to even concurrency across planes.)
  • gzip and spillEnabled were disabled in these demos, so this measures batching in isolation rather than the appender as it would be deployed. Compression is off precisely because the stock <Http> appender cannot compress and leaving it on would vary two things at once; a production deployment should leave both on.
  • Throughput and mean latency are one measurement, not two. The load is closed-loop (oha with no rate limit), so requests/sec is the arithmetic consequence of mean latency, not an independent win. The percentiles are unaffected.
  • New Relic results depend on location. The workers run in Sydney (ap-southeast-2), and Datadog's ap2 site is in the same region. New Relic offers only US and EU regions; these apps ship to the US endpoint (log-api.newrelic.com), so every request crosses the Pacific, which limits how fast the appender can deliver. Requests/sec measures how responsive the app stays, not how many logs arrive. A later delivery-checked run (2026-10-12, engine 0.2.0) found that with this demo configuration (spill off) New Relic batch delivered only about 10–33% of the logs at sustained load, while Datadog delivered 100%. With spill on, every log arrived, but a 5-minute burst took about 12 minutes to drain, and a backlog still on disk is lost if the worker is replaced first. Workers closer to the New Relic region, or gzip plus more flusherThreads, ship faster.
